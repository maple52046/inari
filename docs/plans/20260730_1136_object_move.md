# Object Move (Relocate / Rename)

## 1. Purpose

Records the long-term design of the object **move** capability in the Inari
object browser: relocating and renaming stored objects, within a bucket or across
buckets, from a per-row action or a bulk selection.

It exists so the load-bearing decisions survive the change that produced them —
above all _why_ a move is not a single backend call, and where the safety
invariant that prevents data loss is enforced.

## 3. Consolidated Background

The object browser already listed, downloaded, measured, and deleted objects, but
offered no way to reorganize them. The request was a **Move** button in the
Actions area that opens a dialog for choosing a destination path.

S3-compatible storage has **no move or rename operation**. A move is
`CopyObject` followed by deleting the source. That single fact drives the whole
design, because it forces two things into the open:

1. **A source must never be deleted unless its copy is known to have
   succeeded.** This is the safety invariant of the feature.
2. **A move is not atomic.** Partial outcomes are normal, so results are reported
   per object — including the awkward middle state where the copy landed but the
   source could not be removed.

## 4. Confirmed Decisions

User-confirmed scope:

| Decision                | Choice                                                       |
| ----------------------- | ------------------------------------------------------------ |
| Targets                 | Single object (row action) **and** multi-select bulk move    |
| Destination selection   | Browse existing folders **and** type/edit the path freely    |
| Cross-bucket            | Supported, via a destination bucket selector in the dialog   |
| Objects larger than 5GB | Fully supported through multipart copy (`UploadPartCopy`)    |
| Folders (prefixes)      | Out of scope for now; folder rows keep an empty Actions cell |

Design decisions derived from those choices:

- The port gains storage **primitives** (`copyObject`, `objectExists`), not a
  composite `move` operation.
- "Move" is **application policy** composed from those primitives plus the
  existing `deleteObjects`.
- A move **never overwrites**. An occupied destination is reported as a failure.
- Entries are processed **sequentially**, not concurrently.
- The destination key of each object is resolved by the **UI**, which is what lets
  one request serve both a rename and a bulk move into a folder.

## 5. Architecture and Design Principles

Per `docs/standards/architecture.md`, dependencies point inward and driver
details stay at the edge.

- **`copyObject(input)`** is a genuine backend capability. The 5GiB
  single-request limit and the multipart fallback are driver details that live
  entirely inside the adapter; no inner layer knows they exist.
- **`objectExists(bucket, key)`** is needed to refuse silent overwrites, and
  requires its own port method: `listObjects` cannot answer it, because the
  adapter deliberately filters out the key equal to the requested prefix (the
  folder-marker case) — exactly the row an existence probe asks about.
- **The safety invariant lives in the use case**, not the adapter, so a fake port
  can prove it: copy first, delete only what copied. This is the testability
  property the architecture exists to guarantee.
- The use case stays deliberately dumb: it receives explicit
  `{ key, destinationKey }` pairs and never derives names itself.

## 6. Functional Scope

- A **Move** button on every object row (desktop table and mobile card list) and
  a **Move selected** button in the selection bar.
- A dialog that offers:
  - a destination **bucket** selector (falling back to the current bucket if the
    bucket listing fails, so a same-bucket move stays possible);
  - a **destination folder** path that can be typed or edited freely;
  - a **folder browser** that navigates into subfolders and back to the parent,
    kept in sync with the typed path;
  - a **rename** field when exactly one object is being moved;
  - a preview of the resulting destination;
  - a per-object **result view** after execution, listing failures with reasons.
- After a successful move the listing reconciles itself (see §7).

## 7. Constraints and Rules

### Safety

- **Never delete a source whose copy did not succeed.** The one rule that
  prevents the feature from destroying data.
- **Never overwrite.** An object already at the destination is left untouched and
  reported as a failure.
- **Reject a destination identical to the source in the same bucket.** Without
  this guard, copy-then-delete would delete the object outright.
- Because entries are processed sequentially, an earlier copy is visible to a
  later existence probe, so two sources aimed at one destination cannot both
  proceed.
- Reject an empty destination key, or one ending in `/` (that is a folder).
- A copied key that the delete does not confirm is reported as a failure stating
  that the copy landed but the original remains: the object now exists twice and
  only a human can decide what to do.

### Adapter

- **`CopySource` must be URL-encoded by hand.** The AWS SDK does not encode it,
  so keys holding a space or a non-ASCII character fail with
  `SignatureDoesNotMatch`. Path separators stay literal; only segments are
  escaped.
- **Single-request copy is capped at 5GiB.** Above that: `CreateMultipartUpload`,
  ranged `UploadPartCopy` calls, then `CompleteMultipartUpload`.
- **A multipart upload starts from nothing**, so content type and metadata are
  restated explicitly; unlike `CopyObject` they are not inherited.
- **A failed multipart upload is aborted**, or the incomplete upload lingers
  invisibly and keeps accruing storage cost. The abort is best effort: the
  original failure is what the caller must see, so a failing abort is swallowed.
- Part size is at least 256MB, raised when needed to stay within the
  10,000-part limit.

### Post-move listing reconciliation

Moved keys are removed from the listing and from the selection. A destination
still inside the current location is re-added, because otherwise a move that
lands in view would look like a deletion:

- **Directly in this folder** (a rename): re-added as an object row under its new
  key. The row drops its ETag, because a multipart copy produces a different one
  and showing the old value would be a lie.
- **Deeper down**: re-added as the folder that now holds it — a folder that
  frequently did not exist before the move, which is the point of typing a new
  subpath.

Anything else (another bucket, a sibling folder, a parent) simply leaves the
listing.

### Refresh, broken for the same underlying reason

The listing renders from client state seeded by `useState(initialPage…)`, which
only reads its initial value on mount. `page.tsx` keys the browser by prefix, so
navigating between folders remounts it and works — but a refresh keeps the same
key, so refetched server data was silently discarded and the Refresh button
appeared to do nothing.

Fixed by adopting a newly delivered page **during render**, guarded on the page's
identity (React's documented "adjust state when a prop changes" recipe). The
selection is pruned to keys the new page still contains, since appended
pagination pages are gone and stale keys would inflate the toolbar's count. This
fix is also what lets a move into a freshly created subfolder appear at all.

## 8. Data Model and Format Notes

Domain types (`src/domain/s3/models.ts`), mirroring the existing `DeleteResult`
shape so partial outcomes are expressed consistently:

- `MovedObject` — `{ key, destinationKey }`: reached its destination and no
  longer exists at `key`.
- `MoveFailure` — `{ key, message }`: a normalized, non-sensitive reason.
- `MoveResult` — `{ moved, failed }`: every requested key appears in exactly one
  list. A failure means either the copy never happened _or_ it happened and the
  source survived; the message distinguishes them.

Port types (`src/domain/s3/ports.ts`):

- `CopyObjectInput` — `{ sourceBucket, sourceKey, destinationBucket,
destinationKey }`.

Application types (`src/application/move_objects.ts`):

- `MoveEntry` — `{ key, destinationKey }`, resolved by the UI.
- `MoveObjectsInput` — `{ sourceBucket, destinationBucket, entries }`.

Errors (`src/domain/s3/errors.ts`): a `copy_failed` kind with a user-facing
message, keeping raw SDK errors away from the UI.

Path helpers (`src/lib/object_path.ts`), pure and unit-tested:

- `joinObjectPath(folder, name)` — tolerates the loose paths a user types
  (optional surrounding delimiters) and yields a bare name at the bucket root
  rather than a key with a leading separator, which S3 would read as an unnamed
  first segment.
- `parentPrefix(key)` — the folder portion of a key with its trailing delimiter,
  directly comparable with the prefix a listing was taken at.

## 9. CLI / API / Config Notes

No CLI surface and no new configuration or environment variables.

Server actions in `src/app/(app)/buckets/[bucket]/actions.ts`, following the
established discriminated-result convention (`{ ok: true, … } | { ok: false,
message }`):

- `moveObjectsAction({ sourceBucket, destinationBucket, entries })` →
  `MoveObjectsActionResult`.
- `listBucketNamesAction()` → `BucketNamesResult`, for the destination selector.

The folder browser reuses the existing `loadObjectsAction` rather than adding an
endpoint, reading only the `prefixes` of a listing page.

Port additions to `ObjectStoragePort`:

- `objectExists(bucket, key): Promise<boolean>`
- `copyObject(input: CopyObjectInput): Promise<void>`

## 11. Non-goals

- Moving folders, i.e. recursive prefix moves.
- Overwriting an existing destination, even behind a confirmation.
- Progress reporting for an individual large-object copy.
- Undo.
- Concurrent execution of a bulk move.

## 12. Open Questions

- **Folder moves.** Recorded as out of scope "for now", so whether recursive
  prefix moves are wanted remains undecided.
- **Multipart copy is unverified against a live backend.** The path above 5GiB is
  implemented and type-checked, but no object that large was available to exercise
  it end to end.
- **The folder browser only sees the first listing page** (200 keys), so a
  subfolder appearing beyond it will not be offered. Typing the path still works.
  Whether this needs pagination is unresolved.
- **A newly created folder is appended to the end of the folder list** rather than
  sorted into place, matching how paginated prefixes already merge. Whether that
  ordering should change is open.

## 13. Future Work

- Recursive folder (prefix) moves, if the open question above is answered yes.
- An explicit "replace" path for an occupied destination, with its own
  confirmation, if silently refusing proves too strict in practice.
- Bounded concurrency for bulk moves, which would require replacing the
  sequential collision guard with an explicit reservation of destination keys.
- Progress feedback while a large multipart copy runs.
